### 4.1 Customer ID Generation Strategy

- Generate on backend only (frontend must not submit `customerId` on create).
- Format: `CUS-yyMMdd-######`.
- Example: `CUS-260328-000127`.
- Daily sequence reset rule:
  - `yyMMdd` changes -> sequence restarts from `000001`.
- Uniqueness rule:
  - DB unique index on `customer_id`.
  - Generation runs in transaction with retry on rare conflict.
- Concurrency-safe sequence mechanism (chosen):
  - Use dedicated table `customer_id_sequences(sequence_date char(6) primary key, current_value bigint not null)`.
  - In create flow, execute `SELECT ... FOR UPDATE` on row by `sequence_date=yyMMdd`.
  - If row not exists, insert with `current_value=0`, then lock/update.
  - Increment `current_value`, build id `CUS-yyMMdd-######`, persist partner.
  - Keep unique index on `customer_id` as final safety net.
- Mutability rule:
  - `customer_id` is immutable after create (except optional super-admin override flow).

## 5) API Contract (Draft)

Base: `/api/v1/admin/booking-management/partners`

1. `GET /` list partners
- Query: `page`, `size`, `sort`, `q`, `customerStatus`, `customerType`, `additionTypes`
- Response: paged payload for table.

2. `GET /{id}` detail

3. `POST /` create partner

4. `PUT /{id}` update partner

5. `PATCH /{id}/customer-status` update customer status

6. `DELETE /{id}` soft-delete (default)

7. `POST /{id}/restore` optional restore for soft-deleted records

8. Optional: `POST /batch` bulk create/update for onboarding.

### 5.2 API Contract Details (Implementation-ready)

List endpoint:

- `GET /api/v1/admin/booking-management/partners?page=0&size=20&sort=updatedAt,desc&q=abc&customerStatus=LEAD&customerType=AGENT&additionTypes=CUSTOMER,SHIPPER&additionTypesMode=OR&includeArchived=false`

Sort syntax:

- Repeatable `sort` query, each item: `field,direction`
- Allowed fields: `name`, `customerId`, `customerStatus`, `customerType`, `createdAt`, `updatedAt`
- Direction: `asc` or `desc`

Addition type filter behavior:

- `additionTypesMode=OR` (default): match partner with at least one selected type

### 5.1 CRUD Validation Rules (Draft)

- Required on create:
  - `name`, `taxNumber`, at least one `additionType`.
- Format validation:
  - `contactEmail` must be valid email.
  - `trackingUrl` must be a valid URL if provided.

  - `customerId` generated by backend and unique (case-insensitive compare recommended).

  - PUT replaces editable fields and updates audit fields.

## 6) Security Plan (INTERNAL + Block List)

### 6.1 INTERNAL permission

- Controller-level protection with `ROLE_ADMIN`, `ROLE_EMPLOYEE`, `ROLE_INTERNAL`.
- Verify JWT authority mapping includes `ROLE_INTERNAL` for internal accounts.
- Update Spring Security admin matcher if needed to avoid conflict with controller permissions.
- Security source of truth:
  - Primary enforcement: method security (`@PreAuthorize`) on controllers/services.
  - Secondary guardrail: URL matcher in `SecurityConfig` for `/api/v1/admin/**`.
  - Rule: method security must not be weaker than URL matcher.

### 6.2 Block list / deny list

Because current security has broad public GET matchers in some namespaces, add explicit deny rules for non-admin paths related to booking management:

- Deny public aliases (examples):
  - `/api/v1/booking-management/**`
  - `/api/v1/inquiries/booking-management/**`
- Keep only `/api/v1/admin/booking-management/**` accessible to INTERNAL roles.
- Place deny rules before broad `permitAll` matchers to prevent accidental exposure.

## 10) Risks and Mitigations

1. Risk: Endpoint unintentionally exposed because of broad permit rules.
- Mitigation: use admin-prefixed endpoint + explicit deny-list matcher order.

2. Risk: Large table with many columns degrades UX.
- Mitigation: sticky first columns + horizontal scroll + optional column visibility toggle.

3. Risk: Multi-select addition types difficult to query.
- Mitigation: use normalized join table and indexed filter strategy.

4. Risk: Role mismatch (`ROLE_INTERNAL` vs `ROLE_ADMIN`) causes false 403.
- Mitigation: align matcher + controller preauthorize + integration tests for all INTERNAL variants.
